## Probe D1 / D4 -- Dual-code-space JSON round-trip  · **RESOLVED**

**Question (SCOPE D1):** can a regular `.jac` *and* a `.na.jac` both round-trip a
bridge-representative payload through the shared `json` module -- i.e. is the
`PLAN.md` §5.3 single-source bridge schema viable in native?

**Question (SCOPE D4):** does the native `json` stdlib need a public
`loads`/`dumps` added before this works?

### Verdict

- **D1 = PASS (qualified).** The shared single-source bridge schema **is
  viable.** `import json` resolves to `runtimelib/na_stdlib/json.na.jac` on the
  native pathway (killing the jac-native skill's stale "import json unsupported"
  claim -- the na_stdlib README #6940 is correct). `loads`/`dumps` round-trip the
  full bridge shape -- nested dict, arrays, all scalar types, unicode/emoji --
  with **deep value equality across both code spaces**, both directions.
- **D4 = NO.** Public `def:pub loads` / `def:pub dumps` **already exist** since
  #6950. The earlier scope finding ("only internals exist, must add public API")
  was **stale** on this point and is corrected here. The remaining work is the
  round-trip proof, not API addition.

### Evidence (all green)

```
# Native pathway (compiled binary)
PASS na_dumps_returns_str
PASS na_loads_returns_dict
PASS na_dumps_loads_dumps_idempotent     # dumps(loads(dumps(x))) == dumps(x)
PASS na_repeatable_dump
PASS na_array_roundtrip                  # parser handles arrays + array-of-objects
PASS na_empty_dict / na_empty_list / na_none_roundtrip
WIRE {"id": "evt_001", ... "multiline": "line1\nline2\t\"quoted\" émoji 😀", ...}

# Python pathway (runs the native binary, parses its WIRE with CPython json)
PASS py_loads_native_wire
PASS py_field_*  (id/seq/ratio/active/note/tags/multiline/nested)
PASS py_deep_equality                    # decoded == sample, incl. emoji
PASS py_ascii_reparses_equal / py_utf8_reparses_equal
PYWIRE_UTF8  == native WIRE  (byte-identical: same ", "/": " separators, key order, raw UTF-8)
```

### Two sharp edges (current compiler limits -- do NOT block D1, but constrain bridge encoding)

1. **🔴 Wire MUST use `ensure_ascii=False` (raw UTF-8 JSON).**
   Native `json.loads` **corrupts non-ASCII `\uXXXX` escapes.** Feeding CPython's
   default `ensure_ascii=True` wire (`\u00e9`, surrogate pair `\ud83d\ude00`)
   to native yields `�moji =` instead of `émoji 😀` (`_probe_json_cross`).
   Raw-UTF-8 wire round-trips perfectly both ways (native emits raw UTF-8
   already; CPython must be told `ensure_ascii=False`).
   → **Action:** pin `ensure_ascii=False` in the `PLAN.md` §5.3 bridge encoder.
   Both code spaces then exchange ASCII-or-raw-UTF8 values with zero `\u`
   ambiguity.

2. **🟠 Native arrays MUST be built via `list[any]` + `.append()` -- never list
   literals or typed `list[T]`.** Native codegen crashes or **silently corrupts**
   list literals:
   - `[1, 2, 3]` (literal) → **segfault**
   - `[1, 2, {"y": 1}]` (literal) → builds but dumps as `[1e-323, null, 0]` (garbage)
   - `list[int]` / `list[str]` via literal *or* `.append()` → crash / `[null, 0]`
   - `list[any]` via `.append(scalar)` → ✅ correct (`[1, 2, 3]`)
   - `json.loads("[1,2,3]")` → ✅ correct (the parser builds the list internally)
   → **Action:** Phase 2 bridge code that *constructs* array-bearing values
   natively must use `list[any]` + `.append()`. File the list-literal
   codegen bug against jaclang separately (repros in this file). The parser and
   `dumps` themselves are correct.

### Artifacts

| File | Role |
|---|---|
| `_probe_json_na.na.jac` | Native harness: builds sample (safe list[any]+append), asserts round-trip, emits `WIRE`. |

## Probe D3 -- Pipe partial I/O  · **RETIRED / NON-GATING**

The revised architecture keeps the renderer and embedded managed runtime in one
OS process and exchanges one complete owned value per embed call. There is no
pipe, line reader, partial UTF-8 record, `EAGAIN`, or partial-write problem in
the target seam. Do not build this probe unless a future, separately approved
process-transport proposal revives the question.

## Probe E1 -- Embed ownership and lifecycle  · **PASS (qualified)**

**Question:** can `EmbedRuntime` ownership rules (callable refs, GIL, owned
return strings, repeated release, dispose timeout) be enforced in `.na.jac`, or
is a narrow C/Zig shim required?

### Verdict

**E1 = PASS qualified -- stay in `.na.jac`.** The production host already binds
poll/send, releases the GIL around tty poll, copies Unicode returns, and
finalizes via jacpyembed from native Jac. Phase 0 managed probe confirms
setup/poll/send/stop join behavior. Concentrate C-API into `EmbedRuntime` in
Phase 4; do not introduce a C/Zig shim unless a later ownership failure is
measured.

### Constraints carried forward

- ~~Feed thread is still daemon + 2s join~~ → Phase 3: non-daemon tracked workers
  with `DisposeResult.timed_out` on deadline miss.
- ~~Turn workers are not joined today~~ → Phase 3 stub turns are tracked; legacy
  `ui_send` turn threads still need Phase 6 ownership cleanup.
- ~~`Py_Finalize` skip-on-timeout is Phase 4/6~~ → Phase 4: `EmbedRuntime.finalize_if_safe`
  skips when `mark_workers_safe(False)` after dispose timeout.
